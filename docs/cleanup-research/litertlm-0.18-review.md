# LiteRT-LM Android 0.16.1 → 0.18.0 review

Reviewed 2026-10-13 against the **current, concurrently edited** `/home/yvm/code/Mobie-gpu` worktree. This is a read-only SDK/code review: no app build, adb, emulator, or physical-device run was performed. I compared the two cached Maven AARs (`classes.jar` via `javap`, manifests, POMs, JNI libraries, LICENSE, and THIRD_PARTY_NOTICE) and tagged Kotlin sources/release notes. Findings below separate demonstrated changes from device behavior requiring measurement.

## Blocking issues / release gates

1. **Update the shipped license material before shipping 0.18.0.** `app/src/main/assets/licenses/LiteRT-LM-LICENSE.txt` is byte-for-byte the 0.16.1 AAR `LICENSE` (SHA-256 `c71d239d…`), while 0.18.0's `LICENSE` is `ec40a2da…` and adds 101 lines of MIT/BSD third-party terms. Its `THIRD_PARTY_NOTICE.txt` also changed (2,053,178 → 2,198,164 bytes; SHA-256 `9f22049e…` → `52a70c82…`); there is no matching notice in app assets. Refresh the app's runtime license/notice distribution and check the release APK/AAB contents. The Maven POM still declares Apache-2.0 for LiteRT-LM itself; that does not account for the changed bundled third-party terms. This is an actionable packaging issue, not a claim about a changed primary license.
2. **Qualify the exact Qwen artifact and the 0.18.0 APK on physical ARM64 before declaring GPU support.** Upstream's [0.18.0 notes](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.18.0) mention GPU attention-mask pruning and NPU KV growth, but do not certify `Qwen3-0.6B.litertlm` on Adreno 750 or establish full delegate coverage. The project's `AGENTS.md` requires exact-artifact physical testing. Record SHA-256, quantization, device/Android version, backend/delegate log coverage, peak **CPU and graphics** memory if available, first-token latency, decode tokens/s, thermal behavior, cancellation recovery, and unload/reload memory. `LiteRtGpuBenchmarkTest.kt:37-85` can gather part of this; its `active_backend` assertion shows the selected adapter backend, not the count of graph nodes actually delegated. Include logs proving full delegation. Compare a clean 0.16.1 baseline against 0.18.0 under the same conditions before promising a speed gain.

### Behavior, native packaging, and dependencies

- **GPU and memory:** [0.17.0](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.17.0) reports lower local-attention memory overhead; [0.18.0](https://github.com/google-ai-edge/LiteRT-LM/releases/tag/v0.18.0) reports GPU attention-mask pruning and NPU on-demand KV growth. These are model/backend-dependent native changes. Mobie's `RuntimeLoadMemoryPolicy.kt:19-81`, `LiteRtContextWindowPolicy.kt:8-35`, and `Models.kt:92-126` remain conservative heuristics until measured; do not lower RAM/storage admission solely from release prose. NPU is disabled in `ComputeBackendPolicy.kt:33-40` and cannot be claimed as a v1 gain.
- **Cache:** `EngineConfig.cacheDir` semantics remain: writable directory; unset uses the model directory; `":nocache"` disables cache. Mobie explicitly uses per-model `.litert-cache` at `NativeRuntimeAdapters.kt:539-555`. Version-keyed readiness at `LiteRtCacheState.kt:18-40` invalidates 0.16.1 warm-cache proof on 0.18.0, as intended; retest cold cache size, warm reload, and whether failed GPU attempts leave partial cache files. `CompatibilityResolver.kt:146-153` and `RuntimeLoadStoragePolicy.kt:38-48` budget roughly another model-sized cache from prior measurements.
- **Cancellation / lifecycle:** Tagged `Conversation.kt` preserves the public `sendMessageAsync`, `cancelProcess`, `getTokenCount`, `getBenchmarkInfo`, and `close` signatures; `Session.kt` body is unchanged. The JNI ABI/signatures changed internally. Retest cancel during streaming, reset after cancellation, repeated load/unload, and fallback after failed GPU init. `NativeRuntimeAdapters.kt:294-385,388-423,754-771` depends on correct callback termination and native cleanup. Kotlin Flow cancellation is not a substitute for testing native `cancelProcess`. A [reported 0.17.x source-build GPU cleanup bug](https://github.com/google-ai-edge/LiteRT-LM/issues/3862) is relevant context, but that report explicitly did **not** test Google's Maven AAR; 0.18.0 pins a later LiteRT commit, so do not attribute that bug to 0.18.0 without evidence.
- **Vision/audio:** `visionBackend`/`audioBackend` fields, `Content.ImageFile`, and `maxNumImages` remain public and source-compatible. 0.18.0 adds embedding vision/audio support, not evidence that Mobie's chat vision or audio gained support. Mobie does not configure `audioBackend`; `NativeRuntimeAdapters.kt:425-478` tries GPU vision then CPU then text-only. Retest the exact SmolVLM2 image artifact and fallback paths. No new Android manifest native-library name is required by the AAR.
- **Native library/ABI/minSdk:** Both AARs contain only `jni/arm64-v8a/liblitertlm_jni.so` and `jni/x86_64/liblitertlm_jni.so`; SONAME and `DT_NEEDED` library **set** are unchanged (`libandroid`, `libz`, GLESv2/v3, EGL, dl, log, m, c). Both AAR manifests declare `minSdkVersion=24`; Mobie remains 26. App manifest's optional `libvndksupport.so` and `libOpenCL.so` declarations at `app/src/main/AndroidManifest.xml:17-18` still match [upstream Android guidance](https://github.com/google-ai-edge/LiteRT-LM/blob/v0.18.0/docs/api/kotlin/getting_started.md). They are dynamically loaded GPU dependencies, not packaged JNI sonames. No armeabi-v7a payload exists.
- **Size/dependencies:** AAR 20,189,426 → 20,905,807 bytes (+716,381, +3.55%). Uncompressed arm64 JNI 21,529,648 → 22,155,680 bytes (+626,032); x86_64 25,649,544 → 26,353,160 (+703,616). Actual APK/AAB delta depends on ABI splits and compression. POM updates Gson 2.13.2→2.14.0, `kotlin-reflect` 2.2.21→2.4.0, coroutines-android 1.9.0→1.11.0; verify dependency resolution and release shrinker output. AAR Kotlin metadata is 2.3.0→2.4.0. An isolated Kotlin **2.3.0** compile of `EngineConfig(modelPath=..., backend=Backend.GPU(), maxNumTokens=4096)` against the 0.18.0 JAR succeeded, so the metadata version alone is **not** a demonstrated compile blocker. The full Android build was intentionally not run in the other agent's worktree.
- **License/NOTICE:** AAR `LICENSE` 11,357→16,086 bytes and third-party notice 2,053,178→2,198,164 bytes; both contents changed. Reconcile bundled notices as in the first blocker.

## Opportunities, with safe bounds

1. **Use `ModelInfo` as a local post-download preflight.** Require `ModelInfo.Llm`, check `minRuntimeVersion <= 0.18.0`, input modalities, `supportedBackends(Modality.TEXT)`, `maxContextTokens`, and dynamic-context status before choosing the engine config. Close with `use`. Treat missing/ambiguous metadata as unknown and keep Mobie's existing download-time HF checks. This prevents embedding packages from reaching `Engine` even if HF tags are wrong.
2. **Tune context using measured limits.** For dynamic packages, test `maxNumTokens` within Mobie's existing 1,024–4,096 chat window and at or below `ModelInfo.maxContextTokens()`. A lower context may save KV memory; it may also reduce chat usefulness. Compare 1,024/2,048/4,096 only where the exact artifact supports them, and use measured peak RAM, TTFT, and output quality to decide. Static packages must use their fixed context.
3. **Keep activation type automatic initially.** Null preserves model/backend defaults. For a supported GPU model, compare `FLOAT16` with null; for CPU, compare `FLOAT32` with null. An override is only safe if `Engine.initialize` and generation pass for the exact model/backend. `INT16`/`INT8` have no general safe range; use only on artifacts explicitly supporting them.
4. **Consider speculative decoding only when advertised.** `ConversationConfig.enableSpeculativeDecoding = true` can lazily initialize an MTP drafter even if the engine did not; that may improve decode speed but increases first-use latency/memory. Try null/default first, then true versus false only when `ModelInfo.Llm.hasSpeculativeDecodingSupport()` returns true, with full peak RAM and accuracy tests. Do not enable globally for Qwen without proof.
5. **Vision budget is model-specific.** The new engine-level handling of `ExperimentalFlags.visualTokenBudget` is documented for Gemma 4 only, with choices **70, 140, 280, 560, 1120**. Lower values may cut vision memory/latency but reduce detail. Set before engine initialization and keep later values ≤ the engine's allocation. It is not a Qwen text optimization.
6. **GPU pruning / local attention may help without new app settings.** Benchmark 0.18.0 against 0.16.1 on the same Qwen package and cache state. Apply measured gains to the estimator only after physical data; the NPU KV improvement has no current Mobie v1 path.
